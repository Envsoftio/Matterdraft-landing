Updated 25 November 2026. The first checkpoint is a verified test account completing browser sign-in from a locally packaged Apple Silicon build against the local Nuxt backend. Developer ID signing and notarization are deferred to broader distribution. The pilot opens after a separate clean-Mac run from landing page to first synthetic export.

## Native sign-in contract

- Put browser launch, callback validation, token handling and credential storage in a dedicated Tauri/Rust account module. Vue renders status and triggers actions through narrow commands. Use build-specific portal origin, issuer and the actual registered public client ID. Pin the expected issuer and restrict discovered endpoints to the configured origin. Pilot builds require HTTPS and valid config at startup. Loopback HTTP is a development option.
- Confirm deployed discovery metadata during ONB-01. In the checked-out provider the expected authorization and token paths are `/api/auth/oauth2/authorize` and `/api/auth/oauth2/token`. Use the system browser, Authorization Code with PKCE S256, the exact `legal.matterdraft.studio:/oauth/callback` redirect and a form-encoded token exchange. Request only needed scopes, including `offline_access` if required for refresh. Use the existing consent flow to show the connected identity and allow account switching.
- Keep one short-lived, single-use pending attempt in native memory with a fresh verifier and unpredictable state. Handle callbacks on cold and warm app launch. Match the callback scheme and path exactly. Reject expired or invalid attempts, duplicate parameters, mismatched state and replays. A cold launch without a live attempt gives a restart-sign-in action. Return status to Vue without exposing the callback URL, authorization code, verifier or tokens.
- Store refresh credentials in macOS Keychain and serialize refreshes to avoid rotating the same credential concurrently. Verify token lifetimes, refresh rotation, replay handling and revocation with the registered client. Server-side desktop APIs must validate bearer tokens for the intended resource, client and scope using the provider's supported verification path. Resolve the verified user and current account permissions server-side. The portal cookie session, email in the request, and OIDC ID token carry no desktop API authority.
- Separate account connection, trial status and vault state. A fresh install shows **Connect MatterDraft** before vault setup. A returning user can unlock an existing vault and access permitted files during sign-in or activation failure. A valid signed grant continues offline across ordinary session expiry or browser sign-out. Explicit desktop disconnect clears the local session and active grant, attempts online token revocation when available, and leaves the vault available for permitted actions. Account switching needs fresh authorization and activation for the newly selected account.

## Activation and trial cutover

- Use the same server-side eligibility rule for installer access and desktop activation. Recheck eligibility, verified identity and current account permission when registering or refreshing an installation. Use the server's stable IDs. For this pilot, the proposed eligibility model is an explicit invitation for a verified personal-account owner, linked to that person and account. Confirm this scope before adding the eligibility schema. Existing trial rows alone grant no pilot eligibility.
- Agree the account status, device challenge, activation, refresh and replacement operations before coding their callers. Specify the request and response fixtures, authentication and scope, time units, and error and retry behavior. Distinguish sign-in required, ineligible account, installation already registered, ended trial, invalid proof, temporary service failure and retry after an interrupted response.
- Create an installation key in native code and protect its private material with Keychain, using non-exportable storage where supported. Use a short-lived, single-use server challenge bound to the account, installation key and action. Check current account permission and eligibility at the atomic write that consumes the challenge and records the trial, active installation and audit event. Retain one trial and at most one active trial installation per account under database constraints. A retry after a lost response uses a fresh proof and the original idempotency key to recover the same committed trial dates and registration. Recheck the active generation before signing so a stale refresh cannot restore a replaced installation.
- Keep the original `licence_trial` rows, including ended records, and add schema changes through a new migration. Record a new trial's expiry exactly 168 hours after its first committed activation. Reuse the recorded timestamps for an existing trial, reinstall or recovery. Require recent authentication for replacement, advance the installation generation atomically, and disclose that old offline copies can keep access until their signed deadline.
- In the same release, remove the portal **Start free trial** action, stop its POST endpoint from creating trials, and retain existing status and expiry in account views. Test both old and new API paths against a migrated copy with active and ended records. If a rollback is needed, stop new activations and retain committed trial and installation rows.
- Issue a versioned, asymmetrically signed grant with a trusted key ID, issuer, audience, grant type, entitlement and account IDs, installation key binding, generation, issue time and validity bounds. Keep signing keys server-side and pin trusted public keys in the app. Define rotation and recovery before pilot. Cap the signed deadline at the recorded trial expiry and issue grants from committed state, with safe retry after a signing failure.

## Rust enforcement and vault behavior

Apply a shared decision at operation admission in Tauri/Rust. Inventory the generic `rust_request` dispatcher and direct import, drop, replacement, restore, Save and print preparation commands. Classify by effect since some POSTs inspect existing files and some native Save commands generate new bytes. Preserve the existing single-writer model, worker dispatch, vault checks and deterministic page map. [Tauri command registry](../matterdraft_app/frontend/src-tauri/src/lib.rs) · [Local dispatch and import tools](../matterdraft_app/frontend/src-tauri/src/rust_backend.rs) · [Native Save](../matterdraft_app/frontend/src-tauri/src/native_save.rs) · [Print preparation](../matterdraft_app/frontend/src-tauri/src/native_print.rs)

| With an unlocked vault | Without a valid grant |
| --- | --- |
| Read matters, source and working revisions, open completed exports, save an already generated artifact, back up data and recover vault access | Allow within existing vault permissions |
| Create matters, import or replace files, mutate revisions or settings, submit or retry OCR and builds, generate protected PDFs, Office drafts or split/extract output | Require a valid grant before admitting new work |
| Observe or cancel admitted jobs, commit a completed result, and retrieve that result after expiry | Preserve safe completion and normal cancellation |

Confirm the behavior for restoring a portable backup into an existing vault and for print preparation before enforcing either path. For a queued job, define admission at successful queue acceptance and preserve its authorization across worker retry caused by an internal restart. A user-requested retry is a new admission. Verify expiry against protected server-time history and monotonic elapsed time where applicable. Clock rollback should require online verification for new work and preserve access to existing files. Onboarding and refresh send only account, licence and installation data. Local matter names, file contents, exports and vault credentials stay on the device.
